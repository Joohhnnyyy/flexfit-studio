# Known Issues
Bugs found and chosen not to fix, plus architectural findings.

1. **`classesAttended` logic disconnect:** The application domain implies attendance is tracked by the `checkins` table. However, the `members.profile` endpoint counts `classesAttended` by looking for `bookings` with `status: "attended"`. We will keep this logic intact, but it is a confusing domain model detail discovered during characterization testing.
2. **Time-dependent logic is testable:** The original concern about tightly-coupled time logic (e.g. `FREE_CANCELLATION_HOURS` checking `new Date()`) turned out to be deterministically testable using `vi.useFakeTimers()` in Vitest. No refactoring is strictly necessary to make the clock testable, but we should be aware of it.
3. **Database concurrency limitations:** Local SQLite testing requires `fileParallelism: false` to avoid `SQLITE_BUSY` locks. The application currently works fine in single-threaded tests, but high concurrency might stress this DB setup.
4. **FK teardown fragility:** The `seedFixtures` testing mechanism uses a hand-maintained order of `DELETE FROM` statements to safely traverse the database's Foreign Key dependencies from leaves to roots. This avoids SQL errors but will break (and require manual test suite maintenance) if new relations are added.
5. **Dangling ESLint issues:** During Phase B, a few pre-existing lints (`require("drizzle-orm")` and several unused imports/variables) surfaced when running `pnpm run build` as a production check, because `next build` runs `next lint`. These were cleaned up to allow the build to pass, but the codebase has several `@typescript-eslint/no-unused-vars` warnings lingering across various routers.
6. **Phase A Inventory Gap:** Phase A was declared closed without tracing the entire `_app.ts` router registration list. Consequently, several active routers (`reschedules.ts`, `auth.ts`, `plans.ts`, `payments.ts`, `notifications.ts`, and initially `admin-companies.ts`) were entirely omitted from `01-behavior-inventory.md`. `reschedules.ts` in particular is a complex 11KB router with time-boundary logic that mutates booking states. This oversight is being remediated as part of Phase C restructuring.
7. **Orphaned Backend Endpoints:** Several API endpoints (`reschedules.request`, `reschedules.approve`, `classes.byId`, `classes.update`, `members.adminView`, `trainers.checkAvailability`, `payments.mine`, `payments.createCheckoutSession`) were fully implemented in the backend logic but never integrated into the frontend React UI. We are systematically building out these UIs.
